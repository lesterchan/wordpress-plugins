### 8. wp-postviews — 98/98 PASS after 9 test fixes — 28.5m first run, 22.7m confirming run

First run: 89 passed, 9 failed. **All nine were test defects; the plugin was
right every time.** After the fixes the whole suite was re-run in order and
passed 98/98. `npm run lint:js` clean, `bin/test.sh --filter Metadata` 27/27.

Three separate causes:

**(a) The tab split — 5 failures.** `security.spec.js` still opened the
Settings tab and then filled `#views-template-template` /
`#views-template-most_viewed_template`, which now live on the Templates tab.
Every one timed out waiting for a locator that could never appear.
`helpers.js:492` already had `openTemplates()`; the spec had simply not been
updated with the rest. Fixed at `tests/e2e/security.spec.js` lines 106, 121,
151, 178, 208 — `openSettings( page )` -> `openTemplates( page )`, and the
import swapped to match.

**(b) A fixture that assumed the clock — 2 failures.**
`core.spec.js:81` and `:138` both assert the *unsorted* front-page order.
`beforeAll` created three posts back to back through REST; all three landed in
the same second; WP_Query's default is `ORDER BY post_date DESC` with no
tiebreak, so MySQL returned primary-key order — the exact reverse. The
received array was `[unloved, middling, popular]` against an expected
`[popular, middling, unloved]`, which reads exactly like the plugin leaking its
sort filters into later queries and is not. Fixed by stating the dates:
`date: '2020-01-01T00:00:00'` / `-02` / `-03` on the three `createPost` calls.
The plugin's own sort tests (`?v_sortby=views`) passed throughout.

**(c) An assertion truncation makes impossible — 1 failure.**
`security.spec.js:285` asserted `toContainText( 'window.__pwned' )` on
`#pv-most-chars`, which is `get_most_viewed( '', 5, 12, false )` — a
**12-character** limit. Rendered text was `Hostile <scr... - 42 views`; the
sentinel is 20-odd characters past the cut and could never appear. Replaced
with `toContainText( 'Hostile <scr' )`, which proves more than the old one did:
the payload was not swallowed, its angle bracket is on the page as text rather
than as an element, and the 12 surviving characters pin the order
`get_most_viewed()` does its two jobs in (truncate the raw title, *then*
escape) — escaping first would spend the limit on `&lt;scr`.

**(d) The known `counting.spec.js:245` defect.** Fixed as briefed, by previewing
a draft. `?p=<published>&preview=true` never reaches the preview path at all —
`redirect_canonical()` unsets `is_preview` for an already-public post, strips
the parameter and 301s to `?p=<id>`, so an ordinary post renders and the
counting script is correctly enqueued. Now creates a `status: 'draft'` post,
visits `/?p=<id>&preview=true` (200, no redirect, genuinely a preview), asserts
no counter, then publishes that same post and asserts it counts. One wrinkle
worth recording: this version of `@wordpress/e2e-test-utils-playwright` has
`createPost` but **no `updatePost`** — the publish goes through
`requestUtils.rest({ method: 'POST', path: '/wp/v2/posts/<id>', data: { status: 'publish' } })`.

**Depth: good, with padding.** 98 tests but `display.spec.js:114` is a six-way
parametrised loop over conditional tags and `settings.spec.js:87` a four-way
loop over one select's choices — roughly 15 of the 98 are the same assertion
with a different argument. The CLAUDE.md warning about near-duplicate padding
is justified. It is not shallow, though: both counting paths, the REST field,
the query vars, stored XSS in both directions and the capability gate are all
genuinely covered.

### 9. wp-useronline — 78/79, ONE REAL PLUGIN BUG LEFT FAILING — 21.4m + 20.5m

First run 74/79. Six test defects fixed; the sixth fix then uncovered a genuine
plugin bug, which is left failing. `npm run lint:js` clean,
`bin/test.sh --filter Metadata` 26/26.

**Test defects fixed (6):**

1. **`stats_display` matched two inputs — 3 failures**
   (`settings.spec.js` :86, :332-346, :411). `field()` builds
   `[name="wp_useronline_options[stats_display]"]`, and a Settings API checkbox
   is *two* inputs under one name: the hidden `value="0"` that makes an
   unchecked box post at all, plus the checkbox. Every assertion died of
   Playwright strict mode, not of anything being wrong. Added
   `checkbox( ...keys )` to `helpers.js` beside `field()` — same selector
   prefixed `input[type="checkbox"]` — and used it at all six call sites.

2. **A section heading that was never rendered — 1 failure**
   (`settings.spec.js:97`). Asserted a `Templates` heading on the Templates
   tab. `class-wp-useronline-settings.php:145-150` registers that section with
   an empty title and `__return_empty_string` **on purpose** — one section
   under a tab of the same name would print the word twice. `openTemplates()`
   already asserts the H1 and the active tab, which is the whole identity of
   the screen. Assertion removed, with the reason recorded.

3. **A fixture that only worked on a virgin database — 1 failure**
   (`display.spec.js:305`, `rest_no_route`). It POSTed `/wp/v2/users` and, on
   the "login already taken" error, fell back to
   `rest({ path: '/wp/v2/users?search=...' })` — a query string inside `path`,
   which requestUtils does not accept. So it **passed on the first run against
   a fresh database and failed on every run after**, which is the worst way
   round: a first sweep would have called it green. `helpers.js:583`
   `ensureUser()` exists for exactly this and its docblock says so almost word
   for word. Now `ensureUser( 'useronline_author', 'author', ... )`.

4. **Core's comment form set the sentinel — 1 failure**
   (`security.spec.js:377`). The test logs in as a user whose *display name* is
   `Hostile <script>window.__pwned = 1;</script>` and asserts the page-global
   sentinel stays unset. The fixture already switched the admin bar off for
   that account because core builds "Howdy, %s" from the display name without
   escaping — and then missed core's **other** unescaped surface on the same
   page: `comment_form()`'s "logged-in-as" line, `Logged in as <user_identity>`,
   equally raw. Proved from the trace: the same response carried
   `Logged in as Hostile <script>window.__pwned = 1;</script>` from core and
   `Hostile &lt;script&gt;window.__pwned = 1;&lt;/script&gt;` inside
   `#useronline-details` from the plugin. **The plugin's escaping was correct
   the whole time.** Fixed by creating the fixture post with
   `comment_status: 'closed'`, the same move the fixture already made for the
   admin bar.

**PLUGIN BUG, left failing — `security.spec.js:363`**

Fixing (4) let the test reach its real subject, and it found this. After one
AJAX refresh the document holds **two** elements with `id="useronline-details"`,
nested, and one more on every poll thereafter. Three files, one mismatch:

* `includes/template-tags.php:175` — `users_online_page()` bakes its own
  wrapper into what it returns: `$output = '<div id="useronline-details">' . …`
* `includes/class-wp-useronline.php:227` — the AJAX `details` branch echoes
  that whole thing, wrapper included: `echo wp_kses_post( users_online_page() );`
* `js/wp-useronline.js:33` — `target.innerHTML = html`, where `target` **is**
  `#useronline-details`.

So the refresh writes the container *into itself*. The other three modes are
correct and show what the shape should be: `users_online()`,
`users_browsing_site()` and `users_browsing_page()` emit bare content, and the
wrapper is supplied by the caller (`class-wp-useronline-widget.php:73-81`).
Only `details` carries its wrapper in the payload. Duplicate ids, and a
container that nests one level deeper every `timeout` seconds for as long as
the page is open — so any theme CSS or JS keyed to `#useronline-details` sees a
different element after the first poll.

Fix is a judgement call between three, so I left it: strip the wrapper in the
AJAX branch, have the script use `outerHTML` for `details` only, or move the
wrapper out of `users_online_page()` (that last one changes a documented
template tag's output and the `wp_useronline_page` filter's payload).

**Depth: good.** 79 tests over the recorder, both counting surfaces, the four
template tags, the widget, the shortcode, the AJAX refresh, capability gating
per tab, and stored XSS through the table and through wp_users. Little
padding.

### 10. wp-stats — 93/95, ONE REAL PLUGIN BUG LEFT FAILING — 23.5m + 21.7m

First run 90/95. Three test defects fixed; the remaining two failures are one
genuine plugin bug, reproduced outside Playwright and left standing.
`npm run lint:js` clean.

**Test defects fixed (3):**

1. **A fixture payload eaten before it was stored — 1 failure**
   (`security.spec.js:310`). Asserted the Misc list contained
   `Links <script>`, a hostile *link category* name. `helpers.js:551`
   `insertLink()` created that category with `wp_insert_term()`, which runs the
   name through `wp_filter_kses()` and deletes a script element and its
   contents — so the row said `Links` and the assertion was checking a payload
   that never reached the plugin. The spec's *tag* fixture already avoids this
   by writing the name straight into `$wpdb->terms` after creating the term;
   the link category was simply missed. `insertLink()` now does the same, so
   the name a caller asks for is the name in the row. The plugin escapes both
   correctly — the page renders `Tag <img src=x onerror=...>` as text.

2. **The page-global sentinel, contaminated by core — 2 failures**
   (`security.spec.js:219` and `:304`). Both asserted `window.__pwned` was
   never set, on pages where **core** prints a hostile value unescaped:
   * `:219` is the wp-admin screen, where the admin bar always renders and core
     builds it as `'Howdy, ' . '<span class="display-name">' . $current_user->display_name`
     with no escaping — and this spec's fixture makes the administrator's
     display name a script tag.
   * `:304` browses to the hostile post itself, whose title the theme prints
     with `the_title()`; markup in a post title is a WordPress feature.

   Both now scope to the plugin's own container, which is what the file's other
   tests already do and what the sibling suites settled on. The compensating
   assertions were already present and are kept: `expectNothingArmed()` (no
   `script`, no `[onerror]`, no `[onmouseover]` inside the container) plus
   `toContainText` on the payloads, so escaping that ate the value still fails.

**PLUGIN BUG, left failing — `security.spec.js:256` and `:283`**

**`includes/class-wp-stats-page.php:64` never unslashes `stats_author`.**

```php
$comment_author = sanitize_text_field( (string) get_query_var( 'stats_author' ) );
```

Registered query vars come out of `$_GET`, which `wp_magic_quotes()` has
already slashed; core's own consumers unslash them (`WP_Query::parse_query()`
calls `stripslashes()` on `s`). `sanitize_text_field()` does not remove
backslashes. The docblock immediately above, at **`:56-59`**, states the
opposite — "they arrive as registered query variables rather than out of
`$_GET`, so WordPress has already unslashed them" — which is why this was never
caught.

Consequence: any commenter whose name contains a quote or an apostrophe gets an
empty drill-down and a heading with stray backslashes in it. Reproduced by hand,
outside the suite, against a plain name:

```
GET /?page_id=287&stats_author=Sinead%20O%27Brien
  -> "Comments Posted By Sinead O\&#039;Brien"
  -> "has not made any comments yet."
GET /?page_id=287&stats_author=Grace
  -> "Comments Posted By Grace"  + <blockquote> per comment
```

and confirmed at the query layer:
`WP_Stats_Query::count_comments_by_author( "Zoe \" onmouseover=\"x" )` returns
**1**, `count_comments_by_author( addslashes( ... ) )` returns **0**.

So it is not an XSS — the escaping is right, and `:462` renders the name with
`esc_html()`. It is a correctness bug on the ordinary path: **"Sinead O'Brien"
is enough to trigger it**, and the Comment Members list is the only way into
that view. Fix is `wp_unslash()` before `sanitize_text_field()` at `:64`, and
the docblock at `:56-59` needs correcting with it.

`bin/test.sh --filter Metadata` is **27/28 with 1 pre-existing failure**:
`test_the_upgrade_notice_says_to_update_the_wp_stats_plugins_together`. That is
the known, deliberate one `_standards/RESUME.md` records for wp-polls and
wp-stats, it is about `readme.txt`, and nothing I changed here touches it — my
edits are confined to `tests/e2e/`.

**Depth: good.** 95 tests across the shortcode page, the admin screen, the
widget, the template tags, the `wp_stats_sections` contract, pagination, the
per-tab capability split and stored XSS from five different value sources.

### 11. wp-sweep — 46/70, ONE REAL PLUGIN BUG accounts for 24 of the 24 remaining failures — 17.3m

First run 44/70. Two test defects fixed (REST spec now 8/8). The other **24
failures are all one plugin bug**, reproduced from the captured DOM and left
standing. `npm run lint:js` clean, `bin/test.sh --filter Metadata` passing.

**Test defects fixed (2) — `rest.spec.js:110` and `:124`**

Both did `await expect( requestUtils.rest( … ) ).rejects.toThrow()`.
`requestUtils.rest()` does **`throw json`** on a non-2xx
(`node_modules/@wordpress/e2e-test-utils-playwright/build/request-utils/rest.js:127-128`)
— it rejects with the *parsed error body*, a plain object, not an `Error`. And
`toThrow()` only recognises an `Error`, so it reported "Received function did
not throw" about a call that had rejected exactly as intended. **The plugin was
refusing both correctly all along**, confirmed with curl against the running
container:

```
GET /wp-sweep/v1/sweep/spam_comments  -> 404 {"code":"rest_no_route"}
GET /wp-sweep/v1/count/not_a_sweep    -> 400 {"code":"rest_invalid_param"}
```

Replaced with `rejects.toMatchObject( { code, data: { status } } )`, which is
strictly stronger — it pins *why* the call was refused, so a route that started
500ing would no longer satisfy the test, and 400-not-404 is what proves the name
was rejected by `is_sweep_name_valid()` rather than by there being no such route.

**PLUGIN BUG, 24 tests left failing — `js/wp-sweep-admin.js:65-79`**

**No sweep ever reports its result on the real screen.** Every one of the 24
fails waiting for `.sweep-message .updated`, which is never created.

```js
function messageContainer( row ) {
    const table = row.closest( '.table-sweep' );
    if ( ! table ) { return null; }
    let previous = table.previousElementSibling;
    while ( previous && ! previous.classList.contains( 'sweep-message' ) ) {
        previous = previous.previousElementSibling;
    }
    return previous;
}
```

`table-sweep` is a class on the `<table>` itself
(`includes/class-wp-sweep-list-table.php:60`), and in the rendered screen that
table is **inside the `<form>`** while `.sweep-message` is **outside it**
(`includes/class-wp-sweep-admin.php:197` prints the div, `:201-207` opens the
form and prints the table). Confirmed from the DOM captured in the trace:

```
… <div class="sweep-message"></div> <ul class='subsubsub'> … </ul>
<form …> … <div class="tablenav top"> … </div>
<table class="wp-list-table widefat striped sweeps table-sweep"> …
```

So the walk starts at `.tablenav.top`, runs out of siblings inside the form and
returns `null`; `showMessage()` takes its `if ( ! container ) return;` and exits.

**The sweep itself works** — the AJAX response in the same trace is
`{"success":true,"data":{"sweep":"2 Auto Drafts Processed","count":0,…}}`. Only
the confirmation is lost, on every sweep, for every user.

**Why the unit tests did not catch it, which is the interesting part.**
`tests/js/helpers.js:146-147` builds its fixture as

```html
<div class="sweep-message"></div>
<table class="widefat table-sweep">
```

— adjacent siblings, no `<form>`, no `.tablenav`. `messageContainer()` is
correct against that DOM and only against that DOM. This is precisely the
failure `playwright.config.js:9-14` says the E2E suite exists to catch: "the
test called a function directly and the function was right on its own terms."

Fix is one line in either direction — hoist `.sweep-message` inside the form
just before `$table->display()`, or make `messageContainer()` search from a
common ancestor (`row.closest( 'form' ).parentElement.querySelector( '.sweep-message' )`
or simply `document.querySelector( '.sweep-message' )`, there being one per
screen). **The JS fixture must be corrected in the same change**, or the unit
tests will keep passing against a DOM the plugin does not produce.

The 24: `sweeps.spec.js` :50 :60 :70 :80 :92 :102 :112 :132 :145 :155 :165 :175
:189 :199 :209 :219 :229 :239 :249 :272 :300 (21, all through `sweepRow()` at
`helpers.js:555`), `admin.spec.js:364`, `filters.spec.js:315`,
`security.spec.js:241`.

**Depth: good, and it earned its keep.** 70 tests over the screen, the list
table, bulk actions, all 18 filters, the REST routes, the no-JavaScript path and
stored XSS in details lists. This is the suite that found the most valuable
single defect of the sweep so far.

### 12. wp-downloadmanager — 69/73, FOUR REAL PLUGIN BUGS LEFT FAILING — 15.1m

failures are three distinct plugin bugs, all left standing. `npm run lint:js`

**Test defects fixed (2, both in `settings.spec.js:475`)**

* `.tablenav-pages .total-pages` matched two elements — `WP_List_Table` draws
  its tablenav above *and* below the table — so the assertion died of strict
  mode while both elements said `3`. Now `.first()`.
* With that cleared the test reached a second, older defect:
  `get_user_meta( get_current_user_id(), 'wp_downloadmanager_per_page', true )`
  inside `wpEval()`. `wpEval()` is `wp eval` in the CLI container, which has **no
  logged-in user** — `get_current_user_id()` is `0`, so the read was always
  `get_user_meta( 0, … )` and always `''`. It reported the screen option as
  unsaved while the two assertions above it had just proved it had taken effect.
  Now looks the administrator up by login. The cleanup `delete_user_meta()` two
  lines down was deleting from user 0 for the same reason.

**PLUGIN BUG 1 — the Add File form cannot be submitted as it arrives.**
`admin.spec.js:88`. `includes/class-wp-downloadmanager-admin.php:501`:

```php
<input type="url" class="regular-text" name="file_remote" maxlength="255" data-checks="file_type_2" value="https://" dir="ltr" />
```

`https://` is not a valid URL for HTML5 constraint validation — it has no host —
so the field is invalid the moment the screen loads. It is not `required` and an
*empty* value would be fine; the shipped placeholder value is what breaks it.
The browser therefore cancels the submit, focuses the field and shows a bubble,
and no request is made — however the admin filled the rest of the form and
whichever of the four source radios they picked. The test asks the browser
directly and gets back its own message:

```
file_remote="https://": Please enter a URL.
```

Nothing in `js/wp-downloadmanager-admin.js` disables the field; its `data-checks`
handler only ticks a radio on `focusin`.

**The suite already works around this without naming it.** `helpers.js:538`
`submitFileForm()` blanks `file_remote` before every submit, which is why the
other Add/Edit tests pass — `admin.spec.js:88` is the one test that asks whether
a real person could submit the form, and it is the one that fails. Fix is to
ship `value=""` (or a `placeholder` instead of a value).

**PLUGIN BUG 2 — stored XSS on the downloads page and in the `[download]`
shortcode.** `security.spec.js:103` and `:120`. `%FILE_NAME%` and
`%FILE_DESCRIPTION%` are substituted raw at
`includes/class-wp-downloadmanager-display.php:300` and `:302` — `$file_name` is
just `stripslashes( $file->file_name )`. From the captured DOM of the public
downloads page:

```html
<strong><a href="http://localhost:8899/download/1/">Hostile msasi6th <script>window.__pwned = 1;</script></a></strong>
```

**The plugin is inconsistent with itself, which is what makes this a bug rather
than a design choice.** Three of the five render paths pass the assembled markup
through `wp_kses( …, WP_DownloadManager_Display::allowed_html() )` —
`display.php:1043` (`output()` when it echoes), `widget.php:97` and
`wpstats.php:160,184` — and `output()`'s own docblock says why: "The stats
templates are stored through wp_kses() on save, so this runs the same allow list
back over what comes out of them." The two paths that skip it are the two most
exposed ones: `downloads_page()` returning through
`apply_filters( 'wp_downloadmanager_page', … )` at `:586`, and
`download_embedded()` at `:775`, whose return a shortcode inserts into content
untouched. That is exactly why the widget test at `security.spec.js:139` passes
against the identical hostile row while these two fail.

### Recurring test defects, worth a sweep of their own

Four patterns account for 20 of the 39 fixes, and each will recur in any suite
written the same way:

1. **The Settings API checkbox is two inputs** (wp-useronline ×3, wp-ban,
   wp-email ×4 in a loop, wp-downloadmanager) — a hidden `value="0"` plus the
   box, so `[name="…"]` matches both and dies of Playwright strict mode. Add a
   `checkbox()` helper beside `field()` in every suite that has one.
2. **`get_current_user_id()` inside `wpEval()` is 0** (wp-downloadmanager,
   wp-email, wp-draftsforfriends) — `wp eval` has no logged-in user, so every
   `get_user_meta( get_current_user_id(), … )` read the empty string and the
   assertion reported a working feature as broken.
3. **The page-global XSS sentinel is contaminated by core** (wp-postviews,
   wp-useronline, wp-stats ×2, wp-downloadmanager ×2 — the last two left
   failing for a different reason). Core prints unescaped values on the same
   page: the admin bar's `Howdy, <display name>`, `comment_form()`'s
   `Logged in as …`, and `the_title()`. Scope to the plugin's container, or
   neutralise the core surface as the fixture already did for the admin bar.
4. **Strict mode on selectors that legitimately match twice** — `WP_List_Table`
   draws its tablenav above *and* below (`.total-pages`, `tfoot, tbody`), and
   the Dashboard carries core's own `.notice-error`.

### The 15 plugin bugs, by severity

**Data loss on upgrade — treat as release blockers**
* **wp-print** — the 3.0.0 migration discards the settings of the commonest
  2.58.3 install and stamps itself complete. Irreversible.
* **wp-pluginsused** — the migration deletes the legacy row and writes nothing
  on the `admin_init` path. Limited to installs that ran an unreleased 2.0.0.
* Both are the same shape: correct under WP-CLI, broken on an admin request,
  because `register_setting()` has attached a sanitize callback or a default
  filter that changes what the migration sees.

**Security**
* **wp-downloadmanager** — the downloads page and the `[download]` shortcode
  render `%FILE_NAME%` / `%FILE_DESCRIPTION%` raw, while the widget and the
  WP-Stats sections `wp_kses()` the same markup. Mitigated by `wp_kses_post()`
  on write.
* **wp-print** — the `[print_link]` shortcode does not escape; the template tag
  does.
* **wp-print** — a password-protected post prints its comments to anyone.

**Feature does not work at all**
* **wp-sweep** — no sweep ever reports its result (24 tests).
* **wp-downloadmanager** — the Add File form cannot be submitted as it arrives.
* **wp-email**, **wp-draftsforfriends** — the Screen Options per-page control is
  drawn and silently discarded (no `set-screen-option` filter).
* **wp-useronline** — the AJAX refresh nests `#useronline-details` inside itself
  on every poll.
* **wp-stats** — `stats_author` is never unslashed, so any commenter with an
  apostrophe in their name gets an empty drill-down. *"Sinead O'Brien" is enough.*

**Cosmetic / dead code**
* **wp-downloadmanager** — saving the settings gives no confirmation
  (`settings_errors()` scoped).
* **freemyinternet** — "Settings saved." is printed twice
  (`settings_errors()` called under Settings). The mirror image of the above;
  the rule is *call it iff the screen is not under Settings*.
* **wp-print** — the password form loses its `<form>` and `<input>` to the kses
  allow-list.
* **wp-dbmanager** — a refused download ends in a blank page, and the screen's
  refusal branch is unreachable.

### Suites I judge shallow

None is shallow enough to call green-but-empty. The two thinnest relative to
what they cover:

* **wp-email (45)** — the send assertions lean on the interceptor recording one
  message; no coverage of `[email_link]` placement within content, and the
  standalone page's templates get one render each.
* **wp-postviews (98)** — not shallow, but padded: `display.spec.js:114` is a
  six-way parametrised loop and `settings.spec.js:87` a four-way loop over one
  select, so ~15 of the 98 are one assertion with a different argument. Its
  CLAUDE.md warning about near-duplicate padding is justified.

Everything else earns its count. **wp-sweep is the standout** — its 70 tests
found the single most valuable defect of the sweep, one its own vitest suite
could never see because the JS fixture at `tests/js/helpers.js:146-147` builds a
DOM the plugin does not produce.
